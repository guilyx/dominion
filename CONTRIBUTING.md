# Contributing

## Getting set up

Node.js 18 or newer, and nothing else:

```sh
npm start          # serve the game, no dependencies needed
npm install        # only needed for the desktop app and the browser tests
```

## Before you open a pull request

```sh
npm run test:static   # ~1s, no browser: syntax and game-data consistency
npm run test:smoke    # boots the portable build, plays 5 minutes, saves and loads
```

Both run in CI on every pull request, along with a packaging check that builds
the Electron app and launches it:

```sh
npm run dist:dir       # pack the app without building installers
npm run test:desktop   # launch it and play a land (Linux: prefix with xvfb-run -a)
```

If the machine already has a Chromium, point the smoke test at it instead of
downloading another browser:

```sh
DOMINION_CHROMIUM=/path/to/chrome npm run test:smoke
```

The static checks are the cheap safety net worth extending. They already catch a
building that is missing from the build menu, a category that claims a building
twice, a worker slot table that does not match the upgrade levels, an unlock
that nothing defines, and a bundle that failed to inline a source file. If you
add a data table, add the invariant with it.

## Commit messages drive releases

The project uses [Conventional Commits](https://www.conventionalcommits.org).
[release-please](https://github.com/googleapis/release-please) reads them, keeps
a release pull request up to date, and on merge bumps the version, writes
`CHANGELOG.md`, tags the commit and publishes a GitHub Release with the desktop
binaries attached.

| Prefix | Effect | Example |
| --- | --- | --- |
| `feat:` | minor bump, listed under Features | `feat: add a harbour and fishers` |
| `fix:` | patch bump, listed under Fixes | `fix: stop the build menu overflowing` |
| `perf:` | patch bump, listed under Performance | `perf: cache adjacency for two seconds` |
| `balance:` | patch bump, listed under Game balance | `balance: slow early births` |
| `docs:`, `chore:`, `refactor:`, `test:`, `ci:`, `build:` | no release | `docs: explain the ages` |

A breaking change is a `!` after the type, or a `BREAKING CHANGE:` footer, and
causes a major bump:

```
feat!: drop saves written before the ages update
```

Anything that invalidates existing saves is a breaking change.

## House style

- Plain classic-script JavaScript on `window.BW`. No build step for the game
  itself, no framework, no runtime dependencies.
- Entities are plain data with ids; meshes hang off `_mesh` and are never
  serialized. Keys starting with `_` are stripped when saving.
- Procedural art only: no binary assets in the repo. The application icon is
  generated by `npm run icon`.
- Comment the *why*. The code says what it does.
- Two-space indent, semicolons, single quotes.

## Releasing

Maintainers do not tag by hand. Merging the open release pull request does
everything. To rebuild binaries for an existing tag, run the **Release**
workflow manually and give it the tag.
